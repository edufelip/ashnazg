# v0.3 macOS Apple Silicon MicroVM Implementation Plan

> **For agentic workers:** Use subagent-driven-development with isolated file ownership. No nested agents. Root integrates, verifies independently and publishes separate milestone PRs.

**Goal:** Provide an actual native macOS Apple Silicon `ashnazg up` launcher for a Binder-capable Linux guest running the pinned Android15 ReDroid backend; validate boot and existing Android acceptance locally. iOS remains research.

**Architecture:** An entitled Swift Virtualization.framework helper owns a Linux VM with kernel+ext4 template artifacts, NAT, serial console, virtio-block and virtio-vsock. A minimal Linux guest boots Docker and runs the existing scripts/redroid.py supervisor with a guest bridge as its supervised command. Guest readiness and raw ADB travel over separate vsock ports; the host exposes ADB only on a loopback TCP listener. The Rust CLI delegates VM ownership to the native helper and reports verified runtime state. Keep unknown/unavailable images explicit.

**Tech Stack:** Swift6/Virtualization.framework/Foundation/CryptoKit, native Rust CLI, Linux6.12 ARM64 kernel, Alpine3.22 ARM64 rootfs, Docker, Python standard library guest bridge, GitHub Actions.

## Artifact and bridge contract

Assets directory contains `manifest.json`, `kernel` (uncompressed ARM64 Image), `rootfs.ext4` (read-only template), and optional Android agent/fixture APKs. Manifest schema:

```json
{"schema_version":1,"version":"0.3.0","source_sha":"<40 lowercase hex>","architecture":"aarch64","files":{"kernel":{"sha256":"<64 hex>","size":123},"rootfs.ext4":{"sha256":"<64 hex>","size":456}},"guest":{"kernel_version":"6.12.117","base":"alpine-3.22.8-aarch64","redroid_index":"sha256:81889852444606824d33eb0232fa5813bce3f0993afe871785120af0d7c991ad"}}
```

The source must be actual commit at build time; do not insert a pretend SHA. Manifest/file paths are fixed: reject symlinks/traversal/missing/wrong digests/sizes/platform. Guest builder records original upstream SHA256s, URLs, kernel config and packages in a provenance file; preserve GPL source/config notices. Verify upstream bytes before using them, do not trust a mutable tag alone.

Guest control: AF_VSOCK port10777, bounded newline JSON. Request `{"method":"status"}`; response only after Android supervisor readiness: `{"schema_version":1,"status":"ready","android_serial":"127.0.0.1:5555"}`. A bounded `{"method":"shutdown"}` request from host CID2 acknowledges stopping, asks PID1 to clean up, and powers off. No host commands or arbitrary guest execution API. AF_VSOCK port15555 proxies raw bytes to guest loopback TCP5555 (ReDroid ADB). Guest supports SIGTERM/SIGINT and bounded threads/connections/JSON. Guest services are the child command of scripts/redroid.py, so that supervisor owns container cleanup.

Host helper CLI:
`ashnazg-vm --assets DIR --state-dir DIR [--adb-port15555] [--timeout300] [--validate-only]`
(separate flag/value argv). Validate-only parses/hashes files and VZ config without boot. Normal mode copies the disk template into its exclusively owned state directory, writes serial.log, boots VM with console=hvc0 root=/dev/vda rw init=/sbin/ashnazg-init, connects status10777 until readiness, exposes host loopback adb-port -> guestvsock15555, writes `runtime.json` receipt (no token) and emits exactly one ready JSON line to stdout. It remains running foreground until signal; owns only VM/disk/listener/state. No user-data disk overwrite, foreign process termination, guessed PIDs or blanket cleanup. Safe resource defaults2CPU/2048MiB; record actual settings, never claim the original RAM/boot targets met.

Rust CLI `ashnazg up --assets DIR [--state-dir DIR] [--adb-port15555] [--timeout300] [--vm-helper PATH] [--validate-only]` uses explicit assets first. A missing asset bundle reports actionable setup instructions rather than a fake download URL. Default helper lives alongside the host binary as `ashnazg-vm`. Do not silently route macOS to Docker Desktop or another user's VM. Child status and signals propagate, unsupported OS/arch explicit. Further zero-download/default artifact fetching and agent/MCP auto-connection are required follow-up work before claiming full zero-setup; implement once proven artifacts exist.
